## 这节课在整个热更新流程里的位置

第二版的 `CheckUpdate` 停在了一行注释上：

```csharp
updateInfoCallBack("本地对比文件加载成功");
//3，对比他们，进行AB包下载
```

第三版把"3"补完了，整条链路才真正闭合：

```
下载远端对比文件（ABCompareInfo_TMP.txt）→ 解析成 _remoteABInfoDic
        ↓
读本地对比文件（persistentDataPath 优先，StreamingAssets 兜底）→ _localABInfoDic
        ↓
对比：算出 downLoadList（新增的 + MD5 变了的）
        ↓
删除：本地有、远端没有的包，从 persistentDataPath 删掉
        ↓
下载：DownLoadABFile（最多重试 5 轮）
        ↓
全部成功 → 把远端内容写回本地对比文件
```

一句话：**对比 → 删 → 下 → 写回**，四步顺序不能乱。第二版遗留的 `overCallBack(true)` 也在这版补上了，`Main.cs` 里的成功分支终于会执行。

## 进入方法先清场

```csharp
_localABInfoDic.Clear();
_remoteABInfoDic.Clear();
downLoadList.Clear();
```

`ABUpdateMgr` 是单例，同一个实例可能被调用多次（玩家点"重试"、切场景后再进一次）。

不清的话：

- 字典里上一轮的 key 还在，`abDic.Add(...)` 直接抛 `ArgumentException`（重复的 key）；
- `downLoadList` 会累积上一轮没下完的包，进度分母算错，还会重复下载。

> 这三行是"方法可以重复调用"的前提，别省。

## 对比：哪些要下、哪些要删

### 1. 核心循环

```csharp
foreach (string abName in _remoteABInfoDic.Keys)
{
    // ① 本地没有这个包 → 新增
    if (!_localABInfoDic.ContainsKey(abName))
    {
        downLoadList.Add(abName);
    }
    else
    {
        // ② 本地有，但 MD5 不同 → 更新
        if (_remoteABInfoDic[abName] != _localABInfoDic[abName])
            downLoadList.Add(abName);

        // ③ 远端也有 → 从"待删候选"里划掉
        _localABInfoDic.Remove(abName);
    }
}
```

### 2. 四种情况

| 远端 | 本地 | 判断依据 | 结果 |
|------|------|----------|------|
| 有 | 无 | `ContainsKey` 为 `false` | 进 `downLoadList`（新增） |
| 有 | 有，MD5 不同 | 重载的 `!=` 返回 `true` | 进 `downLoadList`（更新） |
| 有 | 有，MD5 相同 | `!=` 返回 `false` | 跳过，不下载 |
| 无 | 有 | 循环根本遍历不到 | 留在 `_localABInfoDic` → 后面删除 |

第四种是关键：循环只遍历**远端**的 key，远端没有的包永远不会进循环体，自然就留在了 `_localABInfoDic` 里。

### 3. 就地做差集：`_localABInfoDic` 被"用掉"了

遍历结束时，`_localABInfoDic` 里剩下的正好是：

```
本地有 − 远端有 = 需要删除的包
```

也就是说，这个循环一边算"要下的"，一边把 `_localABInfoDic` 从"本地全量"改造成了"待删除列表"。省掉了一个 `List<string> deleteList`，代价是**本地信息被破坏了**——后面再想知道"本地原来有哪些包"已经查不到。

> 本课后面不需要这份全量信息（最后用远端内容覆盖对比文件），所以这么写没问题。如果删除后还要做别的本地判断，就得另存一份。

### 4. 为什么可以边遍历边删

`foreach` 遍历的是 `_remoteABInfoDic.Keys`，删除的是 `_localABInfoDic` —— **两个不同的字典**，各自的迭代器互不干扰。

如果写成：

```csharp
foreach (var kv in _localABInfoDic)
    _localABInfoDic.Remove(kv.Key);   // ❌ InvalidOperationException：集合已被修改
```

运行时就会抛异常。C# 的规则是：`foreach` 期间不能修改**正在被遍历的那个集合**，改别的集合没问题。

### 5. 一个具体例子

本地对比文件：

```
lua 1000 aaa
model 2000 bbb
ui 3000 ccc
```

远端对比文件：

```
lua 1000 aaa
model 2500 bbb2
audio 4000 ddd
```

| 包 | 本地 | 远端 | 结果 |
|----|------|------|------|
| lua | aaa | aaa | 跳过 |
| model | bbb | bbb2 | 下载 |
| audio | 无 | ddd | 下载 |
| ui | ccc | 无 | 删除 |

最终 `downLoadList = ["model", "audio"]`，循环结束后 `_localABInfoDic` 只剩 `ui`。

## 删除：只删可读写目录里的旧包

```csharp
foreach (string abName in _localABInfoDic.Keys)
{
    // 如果可读文件夹中有内容，删除
    // 默认资源中的信息，我们没法删除
    if (File.Exists(Application.persistentDataPath + "/" + abName))
        File.Delete(Application.persistentDataPath + "/" + abName);
}
```

### 1. 为什么这里要判断 `File.Exists`

本地对比文件里记录的包，**不一定真的在 `persistentDataPath` 里**。它可能一直是随包的默认资源，躺在 `StreamingAssets`，从来没下载过。

所以这个判断表达的是：**只删真正落在可读写目录里的文件**，`StreamingAssets` 里的默认资源不碰。

> 严格说，.NET 的 `File.Delete` 对不存在的文件不会抛异常，所以判断不是必需的；但它把"只处理可读写目录"这件事写清楚了，也少一次无谓的系统调用。

### 2. 为什么不能删 `StreamingAssets`

| 原因 | 说明 |
|------|------|
| 技术上删不了 | 只读目录；Android 上还在 APK 里面（`jar:file://...!/assets`） |
| 业务上不该删 | 它是"出厂备份"，玩家清数据/重装后还要靠它启动 |
| 逻辑上不该动 | 它是出厂备份；"删除"的意图通过对比文件表达，而不是靠删默认资源 |

### 3. 为什么先删再下

- 腾空间：大包更新时，设备剩余空间可能不够"新旧两份同时存在"；
- 保证结束时目录里的包与远端清单一致，不留残骸。

顺序反过来（先下后删）也能跑，但先删更符合"先清理、再补齐"的直觉。代价是：从删除到下载完成之间，本地资源是不完整的，所以**热更新必须在进入游戏之前做完**（`Main.cs` 里进度条那个阶段），不能边玩边更。

### 4. 默认资源里的包删不掉，会怎样

首次启动时，本地对比文件来自 `StreamingAssets`，里面列出的包在 `persistentDataPath` 里根本不存在，删除循环会全部跳过 —— 这正是注释里说的"默认资源中的信息，我们没法删除"。

结果是：**文件还在 `StreamingAssets`，只是不再出现在新的本地对比文件里**。

- 如果加载逻辑以对比文件清单为准 → 不会再加载它，等效于删掉了；
- 如果加载逻辑是"`persistentDataPath` 找不到就回退 `StreamingAssets`" → 这个包还能被找到，删除不彻底。

> 彻底解决要么让加载层也以对比文件为准，要么首次启动做物理转存、之后只读 `persistentDataPath`（见《默认资源转存问题》）。这是"逻辑转存"方案留下的一个尾巴。

## 下载：DownLoadABFile 的调整

### 1. 从"自己填列表"变成"只负责下载"

第二版里它是这样的：

```csharp
foreach (string name in _remoteABInfoDic.Keys)
    downLoadList.Add(name);   // 全量下载
```

第三版把这段注释掉了，`downLoadList` 由 `CheckUpdate` 在对比阶段填好。`DownLoadABFile` 现在只做一件事：把列表里的包下下来。

> 职责拆分：**谁决定下什么（对比）** 和 **怎么下（下载）** 分开。下载方法不再需要知道 `_remoteABInfoDic`。

### 2. 进度回调改成字符串

```csharp
updatePro?.Invoke(++downLoadOverNum + "/" + downLoadMaxNum);
```

参数类型从 `UnityAction<int, int>` 变成 `UnityAction<string>`，直接给 `"3/10"` 这样的文本。

好处：`CheckUpdate` 把 `updateInfoCallBack` 原样传下来，进度和"开始更新资源""对比完成"这些提示走**同一个回调**，UI 层一个 `Text` 组件就能全显示，不用再区分"进度用两个 int、提示用一个 string"。

### 3. 重试机制

```csharp
while (downLoadList.Count > 0 && reDownLoadNum > 0)
{
    for (int i = 0; i < downLoadList.Count; i++)
    {
        isOver = false;
        await Task.Run(() =>
        {
            isOver = DownLoadFile(downLoadList[i], localPath + downLoadList[i]);
        });
        if (isOver)
        {
            updatePro?.Invoke(++downLoadOverNum + "/" + downLoadMaxNum);
            tempList.Add(downLoadList[i]);        // 先记录成功
        }
    }
    for (int i = 0; i < tempList.Count; i++)
        downLoadList.Remove(tempList[i]);          // 轮末统一移除
    reDownLoadNum--;
}
```

| 点 | 说明 |
|----|------|
| 一轮扫全表 | 成功的记进 `tempList`，轮末统一从 `downLoadList` 移除 |
| 下一轮只重试失败项 | `downLoadList` 里剩下的就是没下成的 |
| 最多 5 轮 | `reDownLoadNum` 每轮减 1 |
| 进度不回退 | `downLoadOverNum` 只增不减，`downLoadMaxNum` 开头固定 |
| 先记录后删除 | 不在 `for` 里直接 `RemoveAt(i)`，否则索引会跳元素 |

### 4. 两个容易忽略的保护

- **`isOver` 每次下载前置 `false`**：它是个复用变量，上一轮成功会置 `true`，不重置就可能读到上一轮的旧值。
- **`localPath` 在 `await` 之前算好**：`Task.Run` 里跑在线程池，Unity 的 `Application.persistentDataPath` 这类 API 不能保证在后台线程可用（代码注释也写了这点）。

### 5. 边界：没有需要下载的包

如果对比结果 `downLoadList` 为空（全部最新），`while` 直接跳过，最后的 `downLoadList.Count == 0` 为 `true` —— 回调成功，照样会写回对比文件。这是"什么都不用更新"的正常路径，不是异常。

## 收尾：本地对比文件最后才写

```csharp
DownLoadABFile((isOver) =>
{
    if (isOver)
    {
        // 下载完所有AB包文件后，更新本地对比文件
        updateInfoCallBack("更新本地对比文件");
        File.WriteAllText(Application.persistentDataPath + "/ABCompareInfo.txt", remoteInfo);
    }
    overCallBack?.Invoke(isOver);
}, updateInfoCallBack);
```

这行 `File.WriteAllText` 是整条链的**提交动作**：

| 点 | 说明 |
|----|------|
| 只有全部成功才写 | 失败时本地对比文件保持旧版，下次启动重新对比，缺的包会再下 —— 正是"临时文件"方案要的闭环 |
| 写的是内存里的 `remoteInfo` | 它就是 TMP 文件的内容；不用把 TMP 复制一份，少一次读盘 |
| 写完之后优先级变了 | 下次 `GetLocalABCompareFileInfo` 会走 `persistentDataPath` 分支，`StreamingAssets` 的默认资源退居二线 |
| TMP 没删 | 下次下载会覆盖它；想干净可以在成功回调里 `File.Delete(TMP)` |

> 顺序反过来（先写对比文件再下载）就回到了第一版的老问题：下载失败时本地对比文件已经是新的，算不出差量了。

## 接口收窄：能 private 的都 private

| 成员 | 第二版 | 第三版 |
|------|--------|--------|
| `CheckUpdate` | public | public（唯一入口） |
| `DownLoadCompareFile` | public | **private** |
| `GetRemoteABCompareFileInfo` | public | **private** |
| `GetLocalABCompareFileInfo`（两个重载） | public | **private** |
| `DownLoadABFile` | public | **private** |
| `DownLoadABFile` 的 `updatePro` | `UnityAction<int,int>` | `UnityAction<string>` |
| `downLoadList` 的来源 | `DownLoadABFile` 内部全量填充 | `CheckUpdate` 对比阶段填充 |

理由：外部只需要调 `CheckUpdate`。如果把 `DownLoadABFile` 暴露出去，外部直接调时 `downLoadList` 是空的，会"什么都没下就返回成功"——这种误用用 `private` 从编译期就挡掉了。

> 顺带一句：第二版把 `ABInfo` 从 `private` 改成 `public`，是因为 public 方法 `GetRemoteABCompareFileInfo` 的签名里出现了它（CS0051）。这一版相关方法都收回 `private` 了，`ABInfo` 其实可以再变回 `private`，留着 `public` 也不影响运行。

## 易错点

| 易错点 | 说明 |
|--------|------|
| 忘记开头 `Clear` | 第二次 `CheckUpdate` 会因重复 key 抛 `ArgumentException`，`downLoadList` 也会累积 |
| 边遍历边删**同一个**字典 | `InvalidOperationException`；这里删的是另一个字典才安全 |
| 用 `==` 比较 ABInfo | 必须用重载后的 `==`/`!=`（比 MD5）；如果哪天改成 `Equals`，记得同步改调用处 |
| 删除删到 `StreamingAssets` | 那里只读（Android 在 APK 内），也不该删；代码只删 `persistentDataPath` |
| 删除/写文件没有 `try/catch` | 文件被占用（AB 正在加载）、磁盘满都会抛，整个 `CheckUpdate` 中断，`overCallBack` 不执行，UI 卡在"删除无用的文件" |
| 失败时仍写对比文件 | 必须 `if (isOver)` 才写，否则下次启动算不出差量 |
| `overCallBack` 有的分支没 `?.` | `overCallBack(false)` 传 null 会 NRE；要么统一 `?.`，要么在入口判空 |
| `tempList` 跨轮不清空 | 结果不受影响（重复 `Remove` 返回 `false`），但读起来别扭，可每轮 `Clear()` |
| 删除依据是对比文件，不是目录 | 对比文件里没记录的"孤儿文件"永远删不掉；要彻底清理得自己扫目录 |

## 一句话总结

> **对比就是一次差集运算：遍历远端字典，远端有、本地没有 → 新增，MD5 不同 → 更新，同时把"两边都有"的从本地字典里划掉；循环结束后本地字典剩下的就是"远端没有的"，逐个从 `persistentDataPath` 删掉。然后下载 `downLoadList`，最多重试 5 轮，全部成功后才把远端内容写回 `ABCompareInfo.txt` —— 写回是"提交"，失败就不写，保证下次启动还能正确对比。**
